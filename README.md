# MulesoftInsuletWS

AI-assisted MuleSoft development workspace for Insulet. Each agent handles one phase of the integration development lifecycle — from API specification through to build validation, regression testing, and Salesforce verification.

---

## Agents

| Agent | Purpose | Command(s) |
|-------|---------|------------|
| **requirements** | Agile integration user stories, Jira-ready | `/use-requirements` |
| **design** | Solution/technical design (Confluence + Jira ready) from Jira, NotebookLM, SF validation | @mention design rules |
| **migration-design** | Migration design for an existing API (DDD + SF Classic→NextGen) from code, notes, Confluence LLD | `/use-migration-design` |
| **raml** | RAML 1.0 API specification generation | `/use-raml` · `/use-raml-from-jira` · `/use-raml-to-exchange` |
| **develop** | MuleSoft 4 application generation (flows, DataWeave, config) | `/use-develop` |
| **munit** | MUnit 2.x test suite generation | `/use-munit` |
| **testdata** | Live Salesforce test-data resolver for Postman seed payloads | @mention testdata rules |
| **postman** | Postman v2.1 collection generation for HTTP APIs | `/use-postman` |
| **documentation** | Confluence-ready API documentation | `/use-docs` |
| **build** | Maven package + test build validator with auto-fix | `/use-build` |
| **regression** | Postman/Newman regression testing + Salesforce field validation | `/use-regression` |
| **review** | Standards-based code review across all Insulet rulesets | `/use-review` |

### RAML Commands

| Command | What it does |
|---------|-------------|
| `/use-raml` | Generate RAML from a design doc or chat description |
| `/use-raml-from-jira` | Fetch JIRA story + Confluence design, generate RAML locally |
| `/use-raml-to-exchange` | Full end-to-end: JIRA fetch → RAML generation → publish to Anypoint Exchange |

---

## Workflow

```
requirements  →  design  →  raml  →  develop  →  munit  →  build  →  review
                                              ↘  testdata → postman → regression (Newman + SF validation)
                                              ↘  docs     →  review
```

Each agent runs in its own Cursor chat. Output from one agent becomes input to the next — you copy files manually between the `project/` folders as a deliberate review checkpoint.

## Input / Output Folders

| Agent | Drop inputs here | Pick outputs from here |
|-------|-----------------|----------------------|
| requirements | — (Jira ID / five inputs in chat) | `agents/requirements/output/` |
| design | — (Jira / NotebookLM / docs via MCP) | `agents/design/output/` (+ NotebookLM drafts in `agents/design/examples/`) |
| migration-design | `agents/migration-design/input/` (existing API + notes; Confluence LLD via MCP) | `agents/migration-design/output/` |
| raml | `project/input_raml/` | `agents/raml/examples/{api-spec-name}/` |
| develop | `project/input_develop/` | `project/output_develop/` |
| munit | `project/input_munit/` | `project/output_munit/` |
| testdata | — (reads `project/output_develop/`) | `project/input_postman/{api}-seed-payloads.json` |
| postman | `project/input_postman/` | `agents/postman/examples/` |
| documentation | `project/input_docs/` | `project/output_docs/` |
| build | — (points at `project/output_develop/`) | `project/output_build/` |
| regression | — (uses `agents/postman/examples/`) | `project/output_regression/` |
| review | — (point at project via @mention) | Review report in chat |

**What goes in each input folder:**

- `input_raml/` — technical design doc or requirements describing the API
- `input_develop/` — RAML spec + design doc + sample payloads; also stores `jira-*.md` and `confluence-design.md` context files auto-generated by `/use-raml-from-jira`
- `input_munit/` — generated Mule project or specific XML flow files *(also auto-reads `input_develop/` for JIRA/Confluence context)*
- `input_postman/` — RAML spec or MUnit test XML files *(also auto-reads `input_develop/` for JIRA/Confluence context)*
- `input_docs/` — Mule project root reference or supplemental design notes
- `agents/migration-design/input/` — existing (legacy/migrated) Mule API to redesign, plus notes (`.md`/`.txt`); Confluence LLD is pulled via MCP

**Build output** (`project/output_build/`): Maven logs, fix diffs, and build summaries — local-only, git-ignored.

**Regression output** (`project/output_regression/`): Newman HTML/JSON reports and SF validation reports — local-only, git-ignored.
- Newman reports: `{api-name}-{ENV}-{timestamp}.html/.json`
- SF validation reports: `{api-name}-sf-validation/{run_id}-{slug}.md/.html`

## Workspace Structure

```
MulesoftInsuletWS/
├── .cursor/
│   └── commands/          ← slash commands for each agent (+ /list-commands)
├── agents/
│   ├── requirements/      ← Agile user-story generator (rules + output)
│   ├── design/            ← solution-design generator + SF validation + NotebookLM rules
│   ├── migration-design/  ← migration design for existing APIs (+ optional migrated-API delta); inputs in input/ (+ input/migrated-api/), docs in output/
│   ├── raml/              ← rules + examples (reference specs)
│   ├── develop/           ← rules + templates (Mule app templates)
│   ├── munit/             ← rules + examples
│   ├── testdata/          ← live SF test-data resolver (Postman seed payloads)
│   ├── postman/           ← rules + examples (generated collections)
│   ├── documentation/     ← rules + examples
│   ├── build/             ← rules + examples (Maven build validator)
│   ├── regression/        ← rules + templates (Newman + SF validation harness)
│   └── review/            ← 12 review rulesets covering all Insulet standards
├── project/
│   ├── input_raml/        ├── output_raml/
│   ├── input_develop/     ├── output_develop/
│   ├── input_munit/       ├── output_munit/
│   ├── input_postman/     ├── output_postman/
│   ├── input_docs/        ├── output_docs/
│   │                      ├── output_build/      ← build logs (git-ignored)
│   │                      └── output_regression/ ← test reports (git-ignored)
└── regression-tooling/    ← per-API rulesets and sample payloads for SF validation
    └── {api-name}/
        ├── ruleset.yaml
        └── samples/
```

> **Note:** All `agents/*/examples/` folders and all `project/` subfolder contents are git-ignored — they hold local working files only.

## Quick Start

```
1. Open new Cursor chat
2. Type /use-raml  (or whichever agent you need)
3. Place input files in project/input_XX/ if not already there
4. @mention specific files in chat if needed
5. Review the output before using it
```
